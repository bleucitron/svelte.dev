`sv migrate` migre les codebase Svelte et SvelteKit. Les nouvelles migrations utilisent le système
de `sv` de migration par tâche. Les migrations legacy sont déléguées à
[`svelte-migrate@1`](https://www.npmjs.com/package/svelte-migrate) et sont gardées disponibles pour
des projets plus anciens, mais ne seront plus mises à jour.

Avant de migrer, assurez-vous que votre projet a un historique propre, et lisez le changelog de
migration associé ou le guide de migration. Le code de migration ne peut pas prendre en compte
toutes les situations de toutes les applications, il est donc recommandé de bien passer en revue les
changements générés par la migration, et lancez les processus de vérification de votre projet après
chaque étape.

## Usage

```sh
npx sv migrate
```

Quand aucune migration n'est précisée, `sv migrate` vous demande d'en choisir une.

Vous pouvez aussi préciser une migration directement via CLI :

```sh
npx sv migrate [migration]
```

Pour les migrations basées sur des tâches, `sv migrate` affiche les tâches de migration avant de les
appliquer. Les tâches pré-requises sont toujours exécutées, et les tâches restantes peuvent être
sélectionnées de manière interactive ou avec `--tasks`.

Pour rendre les modifications de migrations plus faciles à contrôler, lancez une tâche
sélectionnable à la fois et committez le résultat avant de lancer la suivante. Le système de tâches
est prévu pour créer des commits spécialisés, et non des versions migrées indépendantes. Ne vous
attendez pas à ce que votre projet fonctionne immédiatement après avoir lancé quelques tâches. La
plupart des projets ont besoin que toutes les tâches pertinentes soient appliquées avant que la
migration soit complète.

Après la réussite d'une migration basée sur les tâches, `sv` formatte les changements en utilisant
le `format` ou `fmt` du projet lorsqu'ils existent, ou bien avec Prettier s'il est disponible. Puis
il demande la permission d'installer les dépendances mises à jour. Certains changements laissent des
commentaires `@migration-task` lorsque du travail manuel est nécessaire ; cherchez ce marqueur dans
votre projet avant de considérer que la migration a réussi.

## Migrations basées sur des tâches [!VO]Task-based migrations

### `sveltekit-3`

Met à jour une application SvelteKit 2 vers SvelteKit 3. Lisez le [changelog de SvelteKit
3](https://github.com/sveltejs/kit/blob/main/packages/kit/CHANGELOG.md#300) avant de lancer cette
migration.

La migration est divisée en les tâches suivantes :

- `package-json` (prérequise) met à jour les versions de paquets pour SvelteKit 3.
- `tsconfig` (prérequise) hérite du fichier généré `$app/tsconfig` au lieu de
`.svelte-kit/tsconfig.json`.
- `svelte-config` déplace la configuration supportée du fichier `svelte.config.*` vers
`vite.config.*` et met à jour les imports de l'ancienne configuration lorsque c'est possible.
- `environment` remplace les modules d'environnement dépréciés par `$app/env` et crée les
déclarations `src/env.js` ou `src/env.ts` lorsque nécessaire.
`src/env.ts` declarations when needed.
- `paths` migre les APIs et types `$app/paths` dépréciés.
- `external-redirects` active le nouveau comportement de redirection sur les redirections
extérieures.
- `shallow-routing` remplace les APIs de shallow-routing par des appels `goto`.
- `params` consolide les matchers de paramètres de route dans `src/params.js` ou `src/params.ts`.
- `app-state` migre l'usage de `$app/stores` vers `$app/state`.

La migration ne change que les motifs qu'elle peut identifier de manière certaine. Passez en revue
les commentaires `@migration-task` et le changelog de SvelteKit 3 pour les changements qui
nécessitent du travail manuel.

### `app-state`

Met à jour l'usage de `$app/stores` vers `$app/state` dans les fichiers `.svelte`. Voir le [guide de
migration](/docs/kit/migrating-to-sveltekit-2#SvelteKit-2.12:-$app-stores-deprecated) pour plus de
détails.

## Migrations legacy [!VO]Legacy migrations

Les migrations ci-dessous sont exécutées avec `svelte-migrate@1`. Elles restent disponibles pour que
des projets plus anciens puissent se mettre à jour, mais elles ne recevront plus de corrections ou
de support pour les améliorations à venir. Committez d'abord votre projet et passez en revue leurs
changements avec attention.

### `svelte-5`

Met à jour une application Svelte 4 vers Svelte 5, et modifie les composants pour qu'ils utilisent
les [runes](../svelte/what-are-runes) et les autres syntaxes Svelte 5 ([voir le guide de
migration](../svelte/v5-migration-guide)).

### `self-closing-tags`

Remplace tous les éléments non vides qui s'autoferment dans vos fichiers `.svelte`. Voir la [pull
request dédiée](https://github.com/sveltejs/kit/pull/12128) pour plus de détails.

### `svelte-4`

Met à jour une application Svelte 3 vers Svelte 4 ([voir le guide
migration](../svelte/v4-migration-guide)).

### `sveltekit-2`

Met à jour une application SvelteKit 1 vers SvelteKit 2 ([voir le guide de
migration](../kit/migrating-to-sveltekit-2)).

### `package`

Met à jour une librairie utilisant `@sveltejs/package` de la version 1 à la version 2. Voir la [pull
request dédiée](https://github.com/sveltejs/kit/pull/8922) pour plus de détails.

### `routes`

Met à jour une application SvelteKit pre 1.0 pour qu'elle utilise les conventions de routage de
SvelteKit 1, basées sur le système de fichiers. Voir la [pull request
dédiée](https://github.com/sveltejs/kit/discussions/5774) pour plus de détails.

## Options

Ces options s'applique à la fois aux migrations basées sur les tâches et aux migrations legacy.

### `--cwd <path>`

Lancez la migration dans un environnment de travail différent. Le chemin est par défaut le dossier
courant et doit contenir un fichier `package.json`.

### `--no-git-check`

Par défaut, avant de faire quoi que ce soit, `sv migrate` vous prévient si votre arbre git n'est pas
propre. Utilisez `--no-git-check` pour sauter cette vérification.

### `--confirm`

Ignore la demande de confirmation finale avant d'appliquer la migration. Ceci n'ignore pas la
sélection de migration ou les vérifications d'arbre git ; fournissez un nom de migration et les
options correspondantes pour une utilisation interactive.

## Options de migration basée sur des tâches [!VO]Task-based migration options

Ces options ne s'appliquent pas aux migrations legacy. Les migrations legacy ne supportent pas la
sélection de tâches ou de fichiers, et ont leur propre comportement d'installation de dépendances.

### `--files <glob>`

Limite les fichiers enregistrés par la migration à ceux qui correspondent à un glob. Ceci est une
stratégie de contournement avancée, et non une manière de lancer une migration complète sur une
partie limitée d'un projet. Les tâches font souvent des changements liés sur à la fois des fichiers
de configuration, des fichiers source, et des fichiers générés ; exclure certains de ces fichiers
peut laisser des imports, des configurations, ou des types incohérents, et donc le projet
potentiellement dysfonctionnel.

Une tâche peut tout de même tenter de modifier ou de créer un fichier en dehors du glob. `sv
migrate` n'enregistre pas ce fichier et le signale dans **Unmodified files** (_fichiers non
modifiés_). Passez en revue cette liste et relancez la tâche concernée sans filtre, avec un filtre
plus large, ou faites les changements manquants manuellement.

Lorsque utilisé avec `--cwd`, le glob est relative au dossier courant.

### `--tasks [task...]`

La sélection des tâches de migration sans passer par la sélection interactive. Les tâches
pré-requises sont toujours exécutées car elles posent les bases pour les tâches restantes.

Utilisez `--tasks` sans aucun ID de tâche pour afficher toutes les tâches disponibles pour la
migration sans les lancer.

Utilisez `--tasks all` pour lancer toutes les tâches, ou `--tasks prerequisite` pour lancer
uniquement les tâches pré-requises.

Pour garder les changements passables en revue, lancez un ID de tâche à la fois, examinez et
committez le résultat, puis lancez la tâche suivante. Utilisez `--tasks all` principalement pour
l'automatisation ou lorsqu'un seul diff combiné est intentionnel.

### `--install <package-manager>`

Installez les dépendances avec le gestionnaire de paquets précisé :

- `npm`
- `pnpm`
- `yarn`
- `bun`
- `deno`

### `--no-install`

Ignorez l'installation de dépendances après la migration.
