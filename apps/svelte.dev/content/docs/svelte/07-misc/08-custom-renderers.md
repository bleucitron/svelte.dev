Par défaut, les composants Svelte sont rendus dans le DOM. Un _custom renderer_ ("moteur de rendu
personnalisé") leur permet à la place d'être rendus dans un autre contexte — une scène WebGL, une
interface mobile native, un terminal, un document PDF — pendant que vous continuez d'écrire des
composants Svelte ordinaires avec des states, des props, du contrôle de flux et tout ce à quoi vous
êtes habitué•e•s.

Le renderer est un petit objet qui dit à Svelte comment créer, arranger et mettre à jour les noeuds
de l'environnement cible. Svelte s'occupe du reste.

Cette fonctionnalité est actuellement expérimentale, et il vous faut l'activer en ajoutant l'option
`experimental.customRenderer` là où vous [configurez](/docs/kit/configuration) Svelte, normalement
dans les fichiers `svelte.config.js` ou `vite.config.js` :

```js
/// file: vite.config.js
import { defineConfig } from 'vite';
import { svelte } from '@sveltejs/vite-plugin-svelte';

export default defineConfig({
	plugins: [
		svelte({
			compilerOptions: {
				experimental: {
					+++customRenderer: true+++
				}
			}
		})
	]
});
```

L'API peut évoluer avant que cette fonctionnalité ne soit plus expérimentale.

## Choisir un renderer [!VO]Choosing a renderer

Avec l'option définie comme `true`, les composants vont toujours se rendre dans le DOM, à moins
qu'ils ne déclarent autre chose. Un composant choisit un renderer avec
[`<svelte:options>`](svelte-options), en pointant vers le module qui l'exporte.

```svelte
<!--- file: Scene.svelte --->
<svelte:options customRenderer="three-renderer" />

<script>
	let { speed } = $props();
	let rotation = $state(0);
</script>

<mesh rotation={[0, rotation, 0]} onclick={() => (rotation += speed)}>
	<boxGeometry args={[1, 1, 1]} />
</mesh>
```

> [!NOTE] `three-renderer` est un paquet fictif, utilisé en tant qu'exemple tout au long de cette
> page.

Les éléments utilisés dans un composant de custom renderer — `<mesh>` et `<boxGeometry>` dans notre
cas — n'ont pas de signification particulière pour Svelte. Il fournit leur nom et attributs au
renderer, qui décide comment les traiter.

Le chemin du module est résolu comme n'importe quel autre import dans le composant, ce qui implique
qu'il peut être un nom de paquet, un alias, ou un chemin relatif au composant
(`customRenderer="./renderer.js"`).

### Définir un renderer par défaut [!VO]Setting a default renderer

Si la plupart de vos composants utilisent le même renderer, vous pouvez en faire le renderer par
défaut en passant le chemin du module plutôt que `true` :

```js
/// file: vite.config.js
import { defineConfig } from 'vite';
import { svelte } from '@sveltejs/vite-plugin-svelte';

export default defineConfig({
	plugins: [
		svelte({
			compilerOptions: {
				experimental: {
					+++customRenderer: 'three-renderer'+++
				}
			}
		})
	]
});
```

Les composants individuels peuvent toujours choisir un renderer différent, ou aucun avec
`<svelte:options customRenderer={null} />`.

Chaque composant importe le module du renderer par défaut, ce qui signifie qu'un chemin configuré
globalement ne peut pas être relatif — il serait alors résolu relativement à chaque composant,
plutôt que relativement à votre fichier de configuration. Utilisez un nom de paquet, un import de
sous-chemin comme `#lib/renderer.js` ou un chemin absolu.

### Choisir un renderer par fichier [!VO]Choosing a renderer by file

Pour avoir plus de contrôle, passez une fonction. Celle-ci recevra le nom de fichier de chaque
composant, et renvoit le module de renderer pour ce composant, ou `null` pour cibler le DOM :

```js
/// file: vite.config.js
import { defineConfig } from 'vite';
import { svelte } from '@sveltejs/vite-plugin-svelte';

export default defineConfig({
	plugins: [
		svelte({
			compilerOptions: {
				experimental: {
+++					customRenderer: ({ filename }) => {
						return filename.includes('/src/scene/') ? 'three-renderer' : null;
					}+++
				}
			}
		})
	]
});
```

Puisque la fonction sait pour quel fichier elle doit décider, elle peut également renvoyer un chemin
relatif pour ce fichier. Écrire `<svelte:options customRenderer={...}>` dans un composant a la
priorité sur la fonction.

## L'exécution en dehors du navigateur [!VO]Running outside the browser

Beaucoup de renderers ciblent des environnements qui ne sont pas des navigateurs, comme un terminal,
un générateur de PDFs, un environnement natif, ou un environnement de test. Dans ces environnements,
`svelte` est résolu en son implémentation serveur, qui rend des composants en tant que chaînes de
caractères HTML plutôt que de les exécuter

Pour y utiliser des custom renderers, ajoutez la [condition de
résolution](https://nodejs.org/api/packages.html#conditional-exports) `svelte-custom-renderer`, qui
permet de résoudre `svelte` en tant que l'implémentation qui exécute ces composants. Avec Node,
exécutez votre code avec `--conditions=svelte-custom-renderer`. Si vous utilisez un bundler, ajoutez
`svelte-custom-renderer` à sa liste de conditions de résolution. Si la condition est manquante,
Svelte jette une erreur expliquant comment gérer la situation.

Vos composants ont toujours besoin d'être compilés, comme pour toute application Svelte — par
exemple en les compilant avec Vite et `vite-plugin-svelte`.

Comme exemple, voici une horloge qui est exécutée dans un terminal :

```svelte
<!--- file: Clock.svelte --->
<svelte:options customRenderer="terminal-renderer" />

<script>
	let time = $state(new Date());

	$effect(() => {
		const interval = setInterval(() => (time = new Date()), 1000);
		return () => clearInterval(interval);
	});
</script>

<box border="round" padding={1}>
	<text bold>Il est {time.toLocaleTimeString()}</text>
</box>
```

Pour la lancer, passer le renderer à la fonction [`mount`](svelte#mount), ainsi qu'une cible créée
par ce renderer :

```js
/// file: main.js
// @filename: ambient.d.ts
declare module 'terminal-renderer' {
	interface TerminalRendererFragment {}
	interface TerminalRendererElement {}
	interface TerminalRendererText {}
	interface TerminalRendererComment {}

	type TerminalNodes = {
		fragment: TerminalRendererFragment;
		element: TerminalRendererElement;
		text: TerminalRendererText;
		comment: TerminalRendererComment;
	}

	const renderer: import('svelte/renderer').Renderer<TerminalNodes>;
	export default renderer;

	export function draw(fragment: TerminalRendererFragment): void;
}
// @filename: index.js
// ---cut---
import { mount } from 'svelte';
import renderer, { draw } from 'terminal-renderer';
import Clock from './Clock.svelte';

const screen = renderer.createFragment();

mount(Clock, {
	target: screen,
	renderer
});

// dessine `screen` dans le terminal, puis de nouveau losqu'il change
draw(screen);
```

> [!NOTE] Comme `three-renderer`, `terminal-renderer` est fictif. Un vrai renderer de terminal
> ferait le rendu à l'écran dès que Svelte le mettrait à jour, en appelant des méthodes comme
> `insert` et `setText`.

À chaque seconde, l'effet met à jour `time`, Svelte met à jour le noeud texte à travers le renderer,
et le renderer redessine la scène. Un renderer de PDF travaillerait de la même manière, sauf qu'au
lieu de redessiner en permanence, vous convertiriez le contenu en un fichier PDF à la fin de
l'exécution de `mount`.

Les `props`, les exports de composant et [`unmount`](svelte#unmount) fonctionnent comme ils le
feraient avec le DOM.

## Utilisation dans le navigateur [!VO]Using in the browser

Dans le navigateur, vous pouvez utiliser un composant utilisant un custom renderer au sein d'une
application Svelte classique comme n'importe quel autre composant, à condition que son renderer
supporte le fait d'être utilisé dans le DOM. Ce sera le cas de la plupart des renderers conçus pour
le navigateur, mais référrez-vous à la documentation du renderer, et consultez la section [Combiner
plusieurs renderers](#Mixing-renderers) pour en apprendre plus sur cet usage :

```svelte
<!--- file: App.svelte --->
<script>
	import Scene from './Scene.svelte';
</script>

<h1>Ma scène</h1>

<canvas width="800" height="600">
	<Scene speed={0.1} />
</canvas>
```

Vous pouvez également rendre une application entièrement avec un custom renderer, en passant le
renderer à la fonction [`mount`](svelte#mount) ainsi qu'une cible créée par ce renderer, comme dans
l'[exemple du terminal](#Running-outside-the-browser) un peu plus haut :

```js
/// file: main.js
// @filename: ambient.d.ts
declare module 'three-renderer' {
	interface ThreeRendererFragment {}
	interface ThreeRendererElement {}
	interface ThreeRendererText {}
	interface ThreeRendererComment {}

	type ThreeNodes = {
		fragment: ThreeRendererFragment;
		element: ThreeRendererElement;
		text: ThreeRendererText;
		comment: ThreeRendererComment;
	}

	const renderer: import('svelte/renderer').Renderer<ThreeNodes>;
	export default renderer;

	export function draw(fragment: ThreeRendererFragment): void;
}
// @filename: index.js
// ---cut---
import { mount } from 'svelte';
import renderer from 'three-renderer';
import Scene from './Scene.svelte';

const root = renderer.createFragment();

mount(Scene, {
	target: root,
	renderer,
	props: { speed: 0.1 }
});

// `root` contient désormais les noeuds de la scène
```

## Ce qui est supporté [!VO]What's supported

Les composants utilisant les custom renderers sont compatibles avec la plupart des fonctionnalités
de Svelte, parmi lesquelles les runes, les props, les [snippets](snippet), les composants, le
[contexte](context), les blocs [`{#if}`](if), [`{#each}`](each), [`{#key}`](key) et
[`{#await}`](await), les [`<svelte:boundary>`](svelte-boundary), les
[`<svelte:element>`](svelte-element), les [`attachements`](@attach), les [expressions
`await`](await-expressions), et les directives `bind:` sur les composants.

Les attributs comme `class`, `style`, `class:` et `style:` sont passés au renderer en tant
qu'attributs (voir la section [Écrire un renderer](#Writing-a-renderer)). Les attributs
d'évènements comme `onclick` sont passés à la fonction `addEventListener` du renderer.

Certaines fonctionnalités n'ont de sens que dans le DOM, et provoquent une erreur de compilation
dans les composants utilisant un custom renderer :

- `bind:` sur des éléments
- les [transitions](transition) (`transition:`, `in:` et `out:`) et les [animations](animate)
(`animate:`)
- la directive dépréciée [`on:`](legacy-on)
- [`{@html ...}`](@html)
- [`<svelte:head>`](svelte-head), [`<svelte:window>`](svelte-window),
[`<svelte:document>`](svelte-document) et [`<svelte:body>`](svelte-body)
- `<svelte:options css="injected" />`

### Styles

Svelte continue de scoper la balise `<style>` d'un composant utilisant un custom renderer, en
ajoutant une classe comme `svelte-xyz123` aux éléments auxquels elle s'applique, mais n'injecte pas
les styles dans la page — le fait que votre renderer utilise ou non le CSS est décidé par le
renderer lui-même.

Si `css: 'injected'` est définie dans vos options de compilation (comme c'est le cas en mode
développement dans certaines mises en place), l'option sera ignorée pour les composants utilisant
les custom renderers. Définir `<svelte:options css="injected" />` dans un composant utilisant un
custom renderer provoque une erreur.

### Rendu côté serveur [!VO]Server-side rendering

Les composants utilisant un custom renderer ne font aucun rendu lors du rendu côté serveur. Si un
custom renderer est utilisé dans le navigateur, les composants y seront créés, après le chargement
de la page. Le DOM les entourant est rendu côté serveur et est hydraté normalement.

## Écrire un renderer [!VO]Writing a renderer

L'export par défaut d'un module de renderer est un objet créé avec `createRenderer` importé depuis
`svelte/renderer`. Voici un renderer complet qui fait un rendu en objets JavaScript bruts, qui est
un bon point de départ pour expérimenter. Un vrai renderer se servirait plutôt de la plateforme
qu'il cible — en créant des vues natives, des objets de scène, et ainsi de suite.

```js
// @noErrors
/// file: renderer.js
import { createRenderer } from 'svelte/renderer';

export default createRenderer({
	createFragment() {
		return { type: 'fragment', children: [], parent: null };
	},
	createElement(name) {
		return {
			type: 'element',
			name,
			attributes: {},
			listeners: {},
			children: [],
			parent: null
		};
	},
	createText(data) {
		return { type: 'text', data, parent: null };
	},
	createComment(data) {
		return { type: 'comment', data, parent: null };
	},

	getNodeType(node) {
		return node.type;
	},
	getText(node) {
		return node.data;
	},
	setText(node, text) {
		node.data = text;
	},

	getAttribute(element, name) {
		return element.attributes[name] ?? null;
	},
	setAttribute(element, name, value) {
		element.attributes[name] = value;
	},
	removeAttribute(element, name) {
		delete element.attributes[name];
	},
	hasAttribute(element, name) {
		return name in element.attributes;
	},

	getFirstChild(node) {
		return node.children[0] ?? null;
	},
	getLastChild(node) {
		return node.children.at(-1) ?? null;
	},
	getNextSibling(node) {
		const siblings = node.parent?.children ?? [];
		return siblings[siblings.indexOf(node) + 1] ?? null;
	},
	getParent(node) {
		return node.parent;
	},

	insert(parent, node, anchor) {
		// insérer un fragment insère ses enfants, et le laisse vide
		const nodes = node.type === 'fragment' ? node.children.splice(0) : [node];

		// si besoin, supprimer l'enfant de son parent actuel
		for (const child of nodes) this.remove(child);

		const index = anchor ? parent.children.indexOf(anchor) : parent.children.length;
		parent.children.splice(index, 0, ...nodes);

		for (const child of nodes) child.parent = parent;
	},
	remove(node) {
		if (node.parent) {
			node.parent.children.splice(node.parent.children.indexOf(node), 1);
			node.parent = null;
		}
	},

	addEventListener(element, type, handler) {
		(element.listeners[type] ??= new Set()).add(handler);
	},
	removeEventListener(element, type, handler) {
		element.listeners[type]?.delete(handler);
	}
});
```

> [!NOTE] `createRenderer` renvoie son argument inchangé — son rôle est de fournir du typage.

Les sections suivantes décrivent ce que Svelte attend de chaque méthode.

### Noeuds [!VO]Nodes

Svelte fonctionne avec quatre types de noeuds : les fragments, les éléments, les noeuds texte et les
commentaires. Ils peuvent être n'importe quel type d'objet qui a du sens pour votre renderer.

- `createFragment()` crée un fragment, qui est un conteneur temporaire de plusieurs noeuds.
Lorsqu'un fragment est inséré quelque part, ses enfants y sont déplacés et le fragment est laissé
vide. Les fragments sont également utilisés comme cibles de montage
- `createElement(name)` crée un élément avec le nom fourni, comme `'mesh'` (vous pouvez choisir
quels éléments sont disponibles au sein de votre cible de rendu)
- `createText(data)` créé un noeud texte
- `createComment(data)` crée un commentaire. Svelte utilise les commentaires comme des marqueurs
invisibles, par exemple pour vous souvenir de l'endroit où le contenu d'un bloc `{#if}` va aller, et
n'ont donc pas besoin d'être affichés
- `getNodeType(node)` renvoie `'fragment'`, `'element'`, `'text'` ou `'comment'`
- `getText(node)` renvoie le texte d'un noeud texte, ou les données d'un commentaire
- `setText(node, text)` change le texte d'un noeud texte

### L'arbre [!VO]The tree

- `insert(parent, node, anchor)` insère `node` dans `parent` avant `anchor`, ou à la fin si `anchor`
vaut `null`. Le noeud peut déjà être dans l'arbre, auquel cas il doit être déplacé
- `remove(node)` supprime un noeud de son parent
- `getParent(node)`, `getFirstChild(node)`, `getLastChild(node)` et `getNextSibling(node)` renvoient
le noeud correspondant, ou `null`

### Attributs [!VO]Attributes

- `setAttribute(element, name, value)` est exécutée pour chaque attribut, avec la valeur telle
qu'elle est dans le composant — un nombre, un tableau, un objet, une fonction et ainsi de suite —
plutôt que convertie en tant que chaîne de caractères. Ceci concerne également les attributs étant
des propriétés plutôt que des attributs du DOM comme `value` et `checked`. Le fait que votre
renderer les traite en tant que propriétés, attributs ou autre est à votre discrétion
- `removeAttribute(element, name)` est exécutée à la place de `setAttribute` lorsque la valeur vaut
  `null` ou `undefined`
- `getAttribute(element, name)` renvoie la valeur courante, ou `null` si l'attribut n'est pas défini
- `hasAttribute(element, name)` renvoie si oui ou non l'attribut est défini. Svelte utilise cette
méthode plutôt que de vérifier si `getAttribute` renvoie `null`, afin que dans votre renderer un
attribut puisse être défini et tout de même avoir la valeur `null`

`class` et `style` sont toujours passées en tant que chaînes de caractères. Svelte combine
l'attribut `class` avec toute directive `class:` éventuelle, ainsi qu'avec les classes de scope, et
l'attribut `style` avec toute directive `style:` éventuelle, et en définit le résultat en une seule
passe.

### Évènements [!VO]Events

- `addEventListener(element, type, handler, options)` est exécutée pour les attributs d'évènement
comme `onclick`, avec des `options` décrivant si oui ou non le gestionnaire est de type capture
(`onclickcapture`) ou passif. Appelez `handler` dès que l'évènement se produit — vous pouvez lui
fournir n'importe quels arguments qui ont du sens pour votre renderer, et ils seront fournis au
gestionnaire d'évènement dans le composant
- `removeEventListener(element, type, handler, options)` supprime un gestionnaire. Comme avec le
DOM, Svelte ne l'exécute pas lorqu'un élément est supprimé : un élément et ses gestionnaires sont
censé être supprimés ensemble

### Croisements [!VO]Crossings

`embed` et `host` sont optionnelles, et uniquement nécessaires si votre renderer sera combiné avec
le DOM ou avec d'autres renderers. Ces options sont décrites [plus bas](#Mixing-renderers).

## TypeScript

Si vous écrivez un renderer en TypeScript, passez les types de vos noeuds à `createRenderer`, afin
que les paramètres de chaque méthode soient typés :

```ts
// @noErrors
import { createRenderer } from 'svelte/renderer';

export default createRenderer<{
	fragment: SceneFragment;
	element: SceneObject;
	text: SceneText;
	comment: SceneMarker;
}>({
	// ...
});
```

Si vous ne le faites pas, les types des noeuds seront inférés à partir des types de retour de
`createFragment`, `createElement`, `createText` et `createComment`, tant que ces méthodes
apparaissent en premier dans l'objet. Passer ces types explicitement fournit des messages d'erreur
plus clairs, et permet de ne pas se soucier de l'ordre des champs de l'objet.

Le type `Renderer` est également exporté depuis `svelte/renderer`, pour être utilisé avec du code
qui fonctionne avec des renderers, comme une fonction qui en entoure un. Il prend comme argument un
objet de types de noeuds : `Renderer<{ fragment: ...; element: ...; text: ...; comment: ... }>`.

## Combiner des renderers [!VO]Mixing renderers

Il est possible d'imbriquer des composants qui utilisent des renderers différents, à condition que
les renderers impliqués l'aient prévu. Une page peut contenir une scène 3D, et la scène peut en
retour contenir du contenu DOM, comme des labels HTML positionnés sur les objets 3D. Le contexte,
les props, les snippets, les [frontières d'erreur](svelte-boundary) et la réactivité fonctionnent au
travers des frontières entre renderers.

Si vous utilisez une librairie de renderer, sa documentation devrait vous préciser où ses composants
peuvent être utilisés. Le reste de cette section est destinée au auteurs et autrices de renderers.

L'endroit où le contenu d'un renderer apparaît au sein d'un contenu utilisant un autre renderer est
appelé _crossing_ ("croisement"). Le renderer externe est appelé _host_ ("hôte"), et l'interne est
appelé le _guest_ ("invité"). À chaque crossing, Svelte a besoin deux choses :

- un `container`, géré par le guest, et dans lequel le contenu du guest est rendu
- optionnellement, un `node` géré par le host, qui représente le contenu du guest dans l'arbre du
host. S'il n'y en a pas, Svelte insère un noeud texte vide

Les renderers fournissent ces éléments au travers de deux méthodes optionnelles, `embed` et `host` :

- `embed` est appelée sur le guest. Son exécution signifie "Je veux savoir comment mettre mon
contenu dans l'arbre d'un autre renderer"
- `host` est appelée sur le host. Son exécution signifie "Je veux savoir comment faire de la place
pour un autre renderer"

Svelte essaye d'abord la méthode `embed` du guest, puis la méthode `host` du host. Si aucune de ces
méthodes n'existe, Svelte jette une erreur. Le DOM n'a aucune de ces méthodes, ce qui implique que
dans une application mixte, c'est toujours le custom renderer qui les fournit :

| Situation                                     | Méthode appelée                          | Exemple                                              |
| --------------------------------------------- | ---------------------------------------- | ---------------------------------------------------- |
| Un contenu de custom renderer dans le DOM     | `embed` du custom renderer               | une scène WebGL dans une page normale                |
| Un contenu DOM dans un custom renderer        | `host` du custom renderer                | des labels HTML flottant au-dessus d'une scène 3D    |
| Un contenu d'un renderer A dans un renderer B | A's `embed`, or B's `host` if A has none | un renderer de graphique dans une application native |

Autrement dit : implémentez `embed` si votre renderer sera utilisé dans des apps DOM, ce qui sera le
cas pour la plupart des renderers. Implémentez `host` si du contenu DOM (ou tout autre contenu de
renderer) doit être capable d'être rendu dans l'arbre de votre renderer.

### `embed`

`embed` reçoit le renderer `host` (`null` pour le DOM), ainsi que les `parent` et `anchor` de la
position à laquelle le contenu est rendu. Voici comment un renderer de canvas pourrait s'en servir
pour rendre au sein d'un élément `<canvas>` écrit par l'utilisateur ou l'utilisatrice, ou pour sinon
créer son propre canvas :

```js
// @noErrors
export default createRenderer({
	// ...

	embed({ host, parent }) {
		if (host !== null) {
			throw new Error('Le renderer de canvas peut uniquement être utilisé au sein du DOM');
		}

		const canvas = parent instanceof HTMLCanvasElement ? parent : document.createElement('canvas');
		const scene = create_scene(canvas);

		return {
			// n'insérer un canvas que si nous venons de le créer
			node: canvas === parent ? undefined : canvas,
			// le noeud racine de la scène, dans lequel le contenu est rendu
			container: scene.root,
			// exécuté une fois que le contenu a été supprimé
			destroy: () => scene.dispose()
		};
	}
});
```

Comme dans cet exemple, jeter une erreur est la meilleure manière de rejeter une position que votre
renderer ne supporte pas. C'est également la manière avec laquelle vous pouvez exprimer des
pré-requis comme "seulement au sein d'un `<canvas>`".

### `host`

`host` est l'image de `embed` dans le miroir. Elle reçoit le renderer `guest` (`null` pour le DOM),
et renvoie un `node` venant de votre renderer à mettre dans votre arbre, et un `container`
appartenant au `guest` :

```js
// @noErrors
export default createRenderer({
	// ...

	host({ guest }) {
		if (guest !== null) {
			throw new Error('Seul du contenu DOM peut être rendu dans une scène');
		}

		// un objet de scène qui affiche un élément DOM comme surcouche
		const overlay = create_overlay();

		return {
			node: overlay,
			container: overlay.element,
			destroy: () => overlay.dispose()
		};
	}
});
```

### Règles des crossings [!VO]Rules for crossings

- `embed` et `host` sont exécutées une fois par crossing, de manière synchrone, lorsque le composant
(ou le snippet) est créé. Chaque instance d'un composant a son propre appel.
- `parent` peut n'être encore rattaché à rien. Si le composant est à la racine du markup de son
parent, `parent` est un fragment qui n'a pas encore été inséré, ne mesurez donc pas votre layout et
ne supposez pas au sein de ces méthodes que la page est connectée. Si le composant est directement
dans un élément, comme le `<canvas>` plus haut, `parent` est cet élément.
- Svelte insère et supprime le `node` dans l'arbre du `host`, et insère et supprime le contenu dans
le `container`. `destroy` est exécuté après tout ceci, ne l'utilisez donc que pour libérer vos
propres ressources — ne supprimez pas le `node` ou le contenu lui-même.
- Plusieurs crossings peuvent partager un conteneur, par exemple plusieurs scènes dessinées dans le
même canvas. Svelte garde leur contenu dans le même ordre que leurs noeuds dans l'arbre hôte, y
compris lorsqu'ils sont réordonnés par un bloc `{#each}` à clé.
- Les gestionnaires d'évènments comme `onclick` fonctionnent au seni d'un conteneur DOM, même si le
conteneur ne fait pas partie de la page. Les évènements ne se propagent pas d'un renderer à un
autre.
- Les snippets peuvent être passés entre renderers, tant qu'ils ont été créés par un composant
compilé avec `experimental.customRenderer`. Les snippets créés avec
[`createRawSnippet`](svelte#createRawSnippet) ne peuvent pas être rendus par un custom renderer.
