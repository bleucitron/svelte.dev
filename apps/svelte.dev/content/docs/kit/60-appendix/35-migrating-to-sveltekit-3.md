title: Migrer vers SvelteKit v3
---

SvelteKit 3 supprime certaines fonctionnalités legacy, déplac la configuration hors du fichier
`svelte.config.js` pour la placer dans le plugin Vite, et monte la version minimum de certaines
dépendances. Pour la plupart de ces changements bloquants, vous pouvez automatiquement migrer :

```bash
npx sv migrate sveltekit-3
```

Nous recommandons de d'abord vous mettre à jour de la version 2.x la plus récente avant de passer à
la version 3.0, afin que vous puissiez profiter d'avertissements de dépréciation ciblés.

## Dépendances mises à jour [!VO]Updated dependencies

SvelteKit 3 requiert les versions minimales suivantes :

- Node v22.17
- TypeScript v6
- Svelte v5.57.1
- Vite v8.0.12 (la première version de Vite 8 embarquant la v1 stable de `rolldown`)
- `@sveltejs/vite-plugin-svelte` v7

Mettez à jour les versions de ces paquets dans votre fichier `package.json` et lancez la commande
d'installation de votre gestionnaire de paquets.

## Configuration

### svelte.config.js n'est plus supporté

Plutôt que de déclarer la configuration de votre projet dans le fichier `svelte.config.js`, celle-ci
doit maintenant être passés au plugin `sveltekit` de Vite dans le fichier `vite.config.js`. Les
options qui étaient avant définies dans `config.kit.*` sont maintenant des options de plugins
positionnées à la racine, à côté d'options telles que `compilerOptions` :

```js
// @errors: 2307 ignore adapter auto types missing
/// file: vite.config.js
import { defineConfig } from 'vite';
import { sveltekit } from '@sveltejs/kit/vite';
import adapter from '@sveltejs/adapter-auto';

export default defineConfig({
	plugins: [
+++		sveltekit({
			compilerOptions: { experimental: { async: true }},
			adapter: adapter()
		})+++
	]
});
```

Voir la [documentation sur la configuration](@sveltejs-kit-vite) pour plus d'exemples.

### Options supprimées [!VO]Removed options

Les options suivantes sont obsolètes et devraient être supprimées de votre fichier
`vite.config.js` :

- `files.lib` ([détails](#$lib-is-now-lib))
- `experimental.handleRenderingErrors` n'est plus requis
([détails](#Error-handling-Rendering-errors-are-now-handled))
- `experimental.instrumentation` n'est plus requis ([détails](#Observability))
- `experimental.tracing` est maintenant une option à la racine de `tracing`
([détails](#Observability))
- `vitePlugin` est supprimée — passez plutôt les options de `vite-plugin-svelte` comme `inspector`
directement au plugin
- `preloadStrategy` est supprimée — `modulepreload` est maintenant supportée partout et est donc
toujours utilisée
- `prerender.origin` est supprimée en faveur de `paths.origin`
- `csrf.checkOrigin` est supprimée en faveur de `csrf.trustedOrigins`

### Options ajoutées [!VO]Added options

- `output.linkHeaderPreload` détermine s'il faut utiliser les en-têtes HTTP `Link` pour précharger
des ressources comme les fichiers `.js` et `.css` plutôt que d'injecter des éléments `<link>` dans
le HTML rendu. Ceci peut provoquer des problèmes lorsque les en-têtes deviennent trop volumineuses,
c'est pourquoi SvelteKit 3 utilise plutôt des éléments `<link>` par défaut.
- `csrf.trustedOrigins` vous permet de préciser les origines externes qui sont autorisées à faire
des soumissions de formulaire.
- `paths.origin` remplace `prerender.origin`, et devrait refléter l'origine public de votre
application si elle ne peut pas être correctement dérivée des en-têtes de requête (par exemple parce
que votre application se trouve derrière un proxy). Elle sera utilisée pour les vérification CSRF
des soumissions de formulaire et des appels de fonctions distantes. Si vous utilisez `adapter-node`,
ceci est prioritaire sur la variable d'environnement `ORIGIN`.

### Options modifiées [!VO]Changed options

- `version.pollInterval` est maintenant définie à une heure, ce qui signifie que SvelteKit va
régulièrement vérifier si une nouvelle version de votre application est disponible et mettre à jour
[`updated.current`]($app-state#updated) à `true` si c'est le cas. Auparavant, par défaut aucune
vérification de ce type n'était faite.

## `$lib` is now `#lib` [!VO]`$lib` is now `#lib`

L'alias `$lib` n'est plus généré automatiquement par SvelteKit. Il est remplacé par un alias `#lib`
que vous déclarez dans le champ [`imports`](https://nodejs.org/api/packages.html#subpath-imports) de
votre `package.json`, utilisant les imports de sous-chemins intégrés de Node (que Vite et TypeScript
résolvent nativement). Ajoutez ceci dans votre `package.json`...

```json
/// file: package.json
{
	"imports": {
		"#lib": "./src/lib/index.js",
		"#lib/*": "./src/lib/*"
	}
}
```

... et remplacez `$lib` par `#lib` dans le code de votre application. Notez que vous devrez
également ajouter les extensions de module (par ex. `.js` ou `.ts`) à ces imports.

```js
// @errors: 2307 imported module has no types
---import { foo } from '$lib/foo';---
+++import { foo } from '#lib/foo.js';+++
```

## `$app/environment` (renommé) [!VO] `$app/environment` (renamed)

Le module `$app/environment` a été renommé en [`$app/env`]($app-env). Il peut maintenant être importé
dans votre service worker, là où précédemment si aviez besoin d'accéder à `version` vous deviez
utiliser le module [`$service-worker`](<#$service-worker-(removed)>), désormais supprimé.

## `$app/forms`

Les formulaires utilisant [`use:enhance`]($app-forms#enhance) qui précisent une `action` sur une
page différente vont naviguer vers cette page lors de la soumission, plutôt que de rester sur la
page courante. Ceci permet d'assurer que le comportement amélioré est plus proche du comportement
natif, non amélioré par SvelteKit.

## `$app/manifest`

Un nouveau module [`$app/manifest`]($app-manifest) vous donne accès aux métadonnées de votre
application. Vous pouvez importer ce module partout dans votre application, même dans les service
workers pour des sujets de cache hors-ligne, pour qui vous deviez auparavant utiliser le module
[`$service-worker`](<#$service-worker-(removed)>), maintenant supprimé.

## `$app/navigation`

### Changements du shallow routing [!VO]Changes to shallow routing

Pour le [shallow routing](shallow-routing), `pushState/replaceState` sont dépréciés en faveur de
[`goto`]($app-navigation#goto) :

```js
const state = {};
import { goto } from '$app/navigation';
// ---cut---
// plutôt que ça...
---pushState('/foo', state);---
---replaceState('/bar', state);---

// ... faire ceci :
+++goto('/foo', { shallow: true, state });+++
+++goto('/bar', { shallow: true, replace: true, state });+++
```

Une nouvelle option `persistState: true` permet de réappliquer `page.state` à la suite d'un
rechargement de page.

Le shallow routing déclenche désormais l'exécution des hooks de navigation
([`beforeNavigate`]($app-navigation#beforeNavigate), [`onNavigate`]($app-navigation#onNavigate) et
[`afterNavigate`]($app-navigation#afterNavigate)). Vous pouvez les filtrer en vous basant sur la
propriété `shallow` de l'objet passé à ces hooks de navigation.

### `invalidateAll` est déprécié en faveur de `refreshAll` [!VO]`invalidateAll` is deprecated in favour of `refreshAll`

`invalidateAll` est déprécié en faveur de [`refreshAll`]($app-navigation#refreshAll). La différence
est que `refreshAll` ne réinitialise _pas_ `page.state` en un objet vide, ce qui est généralement ce
que vous souhaitez lorsque vous utilisez le [routing](shallow-routing).

De plus, appeler `invalidateAll()` ou ` invalidate(...)` lors d'une navigation en cours n'annule
plus cette navigation.

### Les options de `goto` sont mises à jour [!VO]`goto` options are updated

En plus de la nouvelle option `shallow` décrite [plus
haut](#$app-navigation-Changes-to-shallow-routing), plusieurs options de
[`goto`]($app-navigation#goto) ont évolué :

- `invalidateAll` est maintenent `refreshAll`, pour refléter le [changement décrit
ci-dessus](#$app-navigation-invalidateAll-is-deprecated-in-favour-of-refreshAll)
- `keepFocus: true` et `noScroll: true` ont été combinées en `reset: false`
- `replaceState` est maintenant `replace`

### `goto` est rejetée pour des URLs qui ne se résolvent pas en une route [!VO]`goto` rejects for URLs that don’t resolve to a route

`goto(...)` est désormais rejetée lorsqu'exécutée avec une URL qui ne résout pas en une route
existante au sein de l'application, ce qui était déjà le cas pour les URLs externes. Pour naviguer
vers une URL externe, utilisez `window.location.href = url`.

### `delta` n'existe que pour les navigations `popstate` [!VO]`delta` only exists for `popstate` navigations

La propriété `delta` des évènements de navigation
([`beforeNavigate`]($app-navigation#beforeNavigate), [`onNavigate`]($app-navigation#onNavigate) et
[`afterNavigate`]($app-navigation#afterNavigate)) existe désormais uniquement pour les navigations
`popstate` (précédent/suivant). Elle vaut `undefined` pour tous les autres types de navigation.

### `preloadData` peut renvoyer un résultat `error` [!VO]`preloadData` can return an `error` result

`preloadData(...)` renvoie désormais `{ type: 'error', status, error }` lorsque la page cible échoue
à se charger, plutôt que de renvoyer `{ type: 'loaded' }` avec un statut 200. Le résultat
`'redirect'` inclut désormais également le `status` correct. Ajoutez une branche `error` à tout code
qui consume le résultat :

```js
import { preloadData } from '$app/navigation';
const url = '/somewhere';
// ---cut---
const result = await preloadData(url);

if (result.type === 'loaded') {
	// ...
+++} else if (result.type === 'error') {
	// faire quelque chose en cas d'erreur
}+++
```

## `$app/paths`

### `base`, `assets`, et `resolveRoute` sont supprimés [!VO]`base`, `assets`, and `resolveRoute` removed

Les exports `base`, `assets` et `resolveRoute` ont été supprimés de [`$app/paths`]($app-paths).
Utilisez plutôt [`asset`]($app-paths#asset) et [`resolve`]($app-paths#resolve) :

```js
let base = '';
let assets = '';
let slug = '';
import { asset, resolve } from '$app/paths';
// ---cut---
// plutôt que ceci...
---const pathname = base + resolveRoute('/blog/[slug]', { slug });---
---const file = assets + '/foo.png';---

// ... faites ceci :
+++const pathname = resolve('/blog/[slug]', { slug });+++
+++const file = asset('foo.png');+++
```

Les types `Pathname` et `Asset` ont également été renommés en `Path` et `AssetPath`, et le préfixe
`/` a été supprimé de ces types — ainsi `asset('/foo.png')` devrait maintenant être
`asset('foo.png')`, et les chemins passés à `resolve` ne commencent plus par `/` (par ex.
`resolve('blog/hello-world')`). Seules les IDs de routes commencent par `/` désormais.

### Les service workers peuvent maintenant importer `$app/paths` [!VO]Service workers can now import `$app/paths`

Auparavant, vous aviez besoin d'importer `base` depuis le module
[`$service-worker`](<#$service-worker-(removed)>), désormais supprimé. Vous pouvez maintenant
utiliser [`asset(...)`]($app-paths#asset) et [`resolve(...)`]($app-paths#resolve) importés depuis
`$app/paths`.

## `$app/service-worker`

Un nouveau module [`$app/service-worker`]($app-service-worker) fournit un accès typé au contexte
d'exécution des service workers dans votre fichier `src/service-worker/index.ts`, à condition que
vous ayez un fichier `src/service-worker/tsconfig.json` qui hérite de
[`$app/tsconfig/service-worker`](#$app-tsconfig-service-worker).

## `$app/state`

### `page.url` est maintenant en lecture seule [!VO]`page.url` is now readonly

`page.url` est maintenant typée comme une `ReadonlyURL` ayant des `ReadonlyURLSearchParams`, ce qui
implique que la muter — par ex. avec `page.url.searchParams.set(...)` ou en assignant
`page.url.pathname` — est désormais une erreur de type. Si vous avez besoin d'une URL mutable,
copiez-la d'abord :

```js
const url = +++new URL(page.url.href);+++
url.searchParams.set('q', 'svelte');
```

### `updated` se met à jour automatiquement [!VO]`updated` updates automatically

La propriété `updated.current` devient `true` lorsque SvelteKit détecte qu'une nouvelle version de
l'application a été déployée. Précédemment, ceci ne se produisait qu'à la suite d'un appel manuel à
`updated.check()`, ou après une navigation ayant échoué. Avec SvelteKit 3, cela se produit plus
souvent :

- pour toute navigation qui déclenche le chargement de données depuis le serveur
- pour tout appel à une fonction distante
- lorsque la fenêtre redevient visible ou reprend le focus (par ex. lorsque vous revenez d'un autre
onglet)
- après un intervalle de polling (qui vaut par défaut une heure)

Notez que si vous utilisez une fonctionnalité comme la [protection
skew](adapter-vercel#Skew-protection) de Vercel, la détection passive lors de la navigation et lors
des appels de fonctions distantes peut provoquer des faux négatifs, puisque la requête est alors
traitée par le déploiement précédent. La détection via polling ou via évènements va continuer de
fonctionner, puisqu'ils contournent la protection skew.

## `$app/stores` (supprimé) [!VO]`$app/stores` (removed)

Le module `$app/stores` (qui exporte les stores `$page`, `$navigating` et `$updated`) a été
supprimé. Utilisez plutôt [`$app/state`]($app-state), qui fournit un [state](../svelte/$state)
Svelte 5, et supprimez le préfixe `$` lorsque vous lisez sa valeur (c-à-d `page` plutôt que
`$page`) :

```svelte
<script>
	import { page } from +++'$app/state'+++;
</script>

<p>chemin actuel : {page.url.pathname}</p>
```

## `$app/tsconfig`

Le fichier `tsconfig.json` de votre projet devrait désormais hériter de `$app/tsconfig` plutôt que
de `./.svelte-kit/tsconfig.json`. Il devrait également préciser les tableaux `include` et `exclude`,
puisque `$app/tsconfig` ne les précise pas :

```json
/// file: tsconfig.json
{
	"extends": "$app/tsconfig",
	"include": ["src", "test", "*"],
	"exclude": ["src/service-worker"]
}
```

Certaines options essentielles de `compilerOptions` (`isolatedModules` et `verbatimModuleSyntax`)
sont incluses dans `$app/tsconfig`, de même que d'autres options que nous recommandons fortement
mais que vous pouvez toujours écraser dans votre propre configuration.

## `$app/tsconfig/service-worker`

Votre service worker nécessite d'être dans un projet TypeScript distinct, autrement les types de
choses comme les évènements `fetch` seront incorrects. Pour faire cela, excluez le service worker de
votre fichier `tsconfig.json` se trouvant à la racine de votre projet, et ajoutez un fichier
`src/service-worker/tsconfig.json` héritant de `$app/tsconfig/service-worker` :

```json
/// file: src/service-worker/tsconfig.json
{
	"extends": "$app/tsconfig/service-worker"
}
```

## `$env/...` (déprécié) [!VO]`$env/...` (deprecated)

Les modules `$env/...` ont été dépréciés en faveur de `$app/env/private` et `$app/env/public` — voir
la section [Variables d'environnement](environment-variables) pour plus d'informations.

## `$service-worker` (supprimé) [!VO]`$service-worker` (removed)

Le module `$service-worker` a été supprimé. Importez plutôt `version` depuis [`$app/env`]($app-env),
`assets`, `immutable` et `prerendered` depuis [`$app/manifest`]($app-manifest), et `resolved` depuis
[`$app/paths`]($app-paths).

## `@sveltejs/kit`

### `error`, `isHttpError`, `redirect`, et `isRedirect` font référence aux types publics [!VO]`error`, `isHttpError`, `redirect`, and `isRedirect` refer to public types

`error`, `isHttpError`, `redirect`, et `isRedirect` font désormais référence aux types publics
plutôt qu'aux classes internes. Si vous importiez les classes internes `HttpError`/`Redirect` depuis
`@sveltejs/kit/internal`, ou si vous utilisiez `instanceof` pour les détecter, utilisez plutôt
`isHttpError`/`isRedirect` importés depuis `@sveltejs/kit`.

### `json` et `text` sont dépréciés [!VO]`json` and `text` are deprecated

Les utilitaires `json(...)` et `text(...)` permettant de générer des réponses sont dépréciés.
Utilisez plutôt `Response.json(...)` et `new Response(text)`.

### `defineParams` a été déplacé vers `@sveltejs/kit/params` [!VO]`defineParams` moved to `@sveltejs/kit/params`

La fonction `defineParams` permettant de créer des [matchers de
paramètres](advanced-routing#Matching) ainsi que les types associés, vit désormais dans le module
[`@sveltejs/kit/params`](@sveltejs-kit-params).

### Les types liés à l'environnement ont été déplacés vers `@sveltejs/kit/env` [!VO]Env-related types moved to `@sveltejs/kit/env`

Les types comme `EnvVarConfig`, utilisé avec le hook
[`defineEnvVars`](@sveltejs-kit-env#defineEnvVars), vivent désormais dans le module
`@sveltejs/kit/env`.

### Les types liés aux hooks ont été déplacés vers `@sveltejs/kit/hooks` [!VO]Hooks-related types moved to `@sveltejs/kit/hooks`

Les types comme `Handle`, qui définissent le type de votre hook [`handle`](hooks#handle), vivent
désormais dans le module `@sveltejs/kit/hooks`.

### Les types des fonctions distantes ont été déplacés vers `$app/server` [!VO]Remote function types moved to `$app/server`

Les types décrivant les fonctions distantes, comme `RemoteQuery`, `RemoteForm` et `RemoteCommand`,
vivent désormais dans le module `$app/server`, à l'instar des fonctions elles-mêmes.

## `@sveltejs/kit/hooks`

La fonction `defineEnvVars` a été déplacée de `@sveltejs/kit/hooks` vers `@sveltejs/kit/env`.

## `@sveltejs/kit/node`

Les utilitaires [`getRequest`](@sveltejs-kit-node#getRequest) et
[`setResponse`](@sveltejs-kit-node#setResponse) sont désormais synchrones et ne renvoient plus de
Promesses. Supprimez `await` des appels faits par les serveurs ou adapteurs Node personnalisés.

## `@sveltejs/kit/node/polyfills` (supprimé) [!VO]`@sveltejs/kit/node/polyfills` (removed)

Le module `@sveltejs/kit/node/polyfills` (et les shims globaux de Node dans `adapter-node` et
`adapter-netlify`) concernait des versions de Node qui ne sont plus supportées. Supprimez toute
déclaration `import '@sveltejs/kit/node/polyfills'` de votre code serveur.

## Sécurité [!VO]Security

### `csrf.checkOrigin` remplacé par `csrf.trustedOrigins` [!VO]`csrf.checkOrigin` replaced by `csrf.trustedOrigins`

L'option dépréciée `csrf.checkOrigin` a été supprimée. La protection CSRF est toujours active ;
plutôt que la supprimer avec `checkOrigin: false`, vous pouvez autoriser des hôtes cross-origine de
confiance avec `csrf.trustedOrigins`.

```js
/// file: vite.config.js
import { defineConfig } from 'vite';
import { sveltekit } from '@sveltejs/kit/vite';
// ---cut---
export default defineConfig({
	plugins: [
		sveltekit({
			csrf: {
				---checkOrigin: false---
				+++trustedOrigins: ['https://trusted-site.com']+++
			}
		})
	]
});
```

### Les soumissions de formulaire cross-origine nécessitent une en-tête `Content-Type` [!VO]Cross-origin form submissions require a `Content-Type` header

Les requêtes cross-origine mutatives qui omettent l'en-tête `Content-Type` sont désormais rejetées
en tant que CSRF. Assurez-vous que les soumissions de formulaire cross-origine incluent une en-tête
`Content-Type`, ou ajoutez l'origine dans `csrf.trustedOrigins`.

### La gestion CORS pour les assets statiques en développment est faite par Vite [!VO]CORS for static assets in development is handled by Vite

SvelteKit ne définit plus par défaut `access-control-allow-origin: *` pour chaque requête d'asset
statique en mode développement. La gestion des CORS est désormais déléguée au middleware intégré de
Vite. Si vous utilisez des accès cross-origine à vos assets statiques lors de votre développement,
configurez-les dans votre configuration Vite :

```js
/// file: vite.config.js
import { defineConfig } from 'vite';
// ---cut---
export default defineConfig({
	server: {
+++		cors: { origin: '*' }+++
	}
});
```

## Cookies

### Mise à jour de `cookie` vers la v2 [!VO]Updated to `cookie` v2

SvelteKit utilise désormais [`cookie`](https://npmx.dev/package/cookie) v2, ce qui implique certains
changements :

- les noms de cookies peuvent contenir uniquement des caractères ASCII. Les caractères non-ASCII (y
compris les caractères Latin-1 Supplement, comme `á`) sont rejetés
- le type `CookieSerializeOptions` a été renommé en `SerializeOptions`
- le type `CookieParseOptions` a été renommé en `ParseOptions`

### Les chemins valent par défaut `'/'` [!VO]Paths default to `'/'`

Lorsque vous définissez un cookie sans `path` explicite (ce qui était auparavant interdit), le
chemin vaut désormais `/` par défaut plutôt que le chemin de la requête actuelle, ce qui signifie
que les cookies s'appliquent sur tout le site. Ceci correspond au comportement attendu la plupart du
temps. Vous pouvez passer un `path` explicite si vous en avez le besoin :

```ts
declare const cookies: import('@sveltejs/kit').Cookies;
declare const name: string;
declare const value: string;
// ---cut---
cookies.set(name, value, +++{ path: '/some/path' }+++);
```

## Gestion des erreurs [!VO]Error handling

### `App.Error` inclut toujours `status` [!VO]`App.Error` always includes `status`

Un objet `App.Error`, comme la prop `error` d'un composant `+error.svelte`, a une propriété `status`
reflétant le statut HTTP de l'erreur l'ayant provoqué (par ex. 404 pour une erreur Not Found, ou 500
pour une erreur interne générique), en plus de `message` et de toutes les propriétés que vous
pourriez définir dans votre fichier [`app.d.ts`](types#app.d.ts).

### Les arguments de `error(...)` ont changé [!VO]`error(...)` arguments changed

Précédemment, le deuxième argument de [`error(...)`](@sveltejs-kit#error) pouvait être soit le
`message` en tant que `string`, soit un objet contenant un champ `message` en plus d'autres
propriétés additionnelles définies dans `app.d.ts` (comme un `code` de suivi).

Désormais, le deuxième argument doit toujours être une `string`. Si vous avez besoin de fournir
d'autres propriétés, vous devrez les passer en troisième argument.

### `handleValidationError` est supprimée [!VO]`handleValidationError` is removed

Les erreurs de validation sont désormais passées à [`handleError`](hooks#handleError) avec `'kind:
validation'`. L'objet générique `{ status, message }` peut être retourné sans risques, tandis que
les `issues` de validation permettant de faire du logging ou de la gestion personnalisée sont
fournies séparémment.

### `handleError` reçoit toutes les erreurs [!VO]`handleError` receives all errors

Avec SvelteKit 2, `handleError` n'était pas appelée dans le cas d'erreurs _attendues_, c'est-à-dire
celles créées avec l'utilitaire [`error(...)`](@sveltejs-kit#error). Avec SvelteKit 3, _toutes_ les
erreurs sont passées à `handleError`. Voir la [documentation](hooks#handleError) pour plus
d'informations.

### `handleError` peut influencer le statut [!VO]`handleError` can influence the status code

Si vous avez besoin de contrôler le code HTTP de statut pour afficher une page dans le cas d'une
erreur, vous pouvez renvoyer une propriété `status` depuis `handleError` en plus des autres
propriétés requises par `App.Error`.

### Les erreurs de rendu sont désormais gérées [!VO]Rendering errors are now handled

Les erreurs jetées lors du rendu sont désormais toujours passées à `handleError` puis à la
[frontière d'erreur](../svelte/svelte-boundary) la plus proche. Des frontières d'erreur sont
automatiquement créées pour chacun de vos composants `+error.svelte`.

Si vous avez un hook `handleError` asynchrone dans le fichier `hooks.client.ts`, activez
`compilerOptions.experimental.async` dans les options de plugin `sveltekit(...)` de votre
configuration Vite afin qu'il puisse bénéficier de `await` lors du rendu.

### Les réponses des actions de formulaires utilisent le code de statut `fail` [!VO]Form action responses use the `fail` status code

Les réponses améliorées d'actions de formulaire utilisent désormais le code de statut HTTP passé à
`fail(...)` plutôt que de systématiquement renvoyer `200`. Si vous inspectez les codes de statut des
soumissions de formulaire amélioriées (par exemple dans un callback `use:enhance` ou lors de tests),
ces codes réflètent désormais la valeur passée à `fail`.

### Les sourcemaps sont appliquées [!VO]Sourcemaps are applied

Les sourcemaps sont générées par défaut, et appliquées aux stack traces lorsque les erreurs se
produisent. Pour que ceci fonctionne en production (plutôt qu'avec `vite preview`), les adaptateurs
doivent éviter tout changement destructeur (comme recompiler sans générer de sourcemaps
supplémentaires et correctes). Pour les adaptateurs officiels, ce travail est actuellement en cours.

## Paramètres [!VO]Params

Les [matchers de paramêtres](advanced-routing#Matching) ne sont plus des fichiers dans le dossier
`src/params`. Déclarez tous vos matchers dans un unique fichier `src/params.ts` (ou `src/params.js`)
en utilisant l'utilitaire `defineParams`. Un matcher peut être une fonction qui renvoie une valeur
parsée (ou `undefined`, si le paramètre ne correspond pas), ou un [Standard
Schema](https://standardschema.dev).

```js
/// file: src/params.js
import { defineParams } from '@sveltejs/kit/params';
import * as v from 'valibot';

export const params = defineParams({
	// avec un schéma
	integer: v.pipe(v.string(), v.toNumber()),

	// avec une fonction
	fruit: (param) => {
		if (param === 'apple' || param === 'orange') {
			return param;
		}
	}
});
```

## Observabilité [!VO]Observability

L'[instrumentation](observability) serveur se déclenche désormais automatiquement si un fichier
`src/instrumentation.server.js` existe.

Pour activer le suivi [OpenTelemetry](https://opentelemetry.io/), ajoutez une configuration
`tracing.server` :

```js
import { defineConfig } from 'vite';
import { sveltekit } from '@sveltejs/kit/vite';
/// file: vite.config.js
// ---cut---
export default defineConfig({
	plugins: [
		sveltekit({
			+++tracing: { server: true }+++
		})
	]
});
```

## Adaptateurs [!VO]Adapters

Tous les adaptateurs officiels requièrent désormais SvelteKit 3, en plus des changements spécifiques
suivants :

### `adapter-cloudflare`

Les APIs spécifiques à Cloudflare ne sont plus disponibles dans `platform`. À la place, vous les
trouverez là où vous les trouveriez dans un worker Cloudflare :

- `env`, `ctx.waitUntil`, et les autres propriétés `ctx` doivent être importées depuis
`cloudflare:workers` :
```js
// @filename: ambient.d.ts
declare module 'cloudflare:workers' {
	export const env: { KV: { get(): Promise<unknown> } };
	export function waitUntil(promise: Promise<any>): void;
}
// ---cut---
import { env, waitUntil } from 'cloudflare:workers';

const value = await env.KV.get('key');
```
- `cf` est désormais une propriété de l'objet `Request` :
```js
/// file: src/routes/cf/+server.js
// @filename: ambient.d.ts
interface Request {
  cf: import('@cloudflare/workers-types').IncomingRequestCfProperties;
}
// @filename: index.js
// @errors: 7031
// ---cut---
export async function GET({ request }) {
	const { country } = request.cf;
}
```
- `caches` est maintenant une variable globale :
```js
/// file: src/routes/cache/+server.js
let request = new Request('');
// ---cut---
const myCache = await caches.open('foo');
await myCache.match(request);
```

- Pour rendre ces types disponibles dans votre application, installez
[`wrangler`](https://www.npmjs.com/package/wrangler) et lancez [`wrangler
types`](https://developers.cloudflare.com/workers/languages/typescript/).


- la version minimum de `wrangler` est désormais `^4.67.0`
- `@cloudflare/workers-types` a été mis à jour

### `adapter-node`

- la compilation est désormais effectuée par `rolldown`
- les assets statiques sont servis depuis une liste enregistrée au moment de la compilation ; les
fichiers ajoutés a posteriori dans le dossier compilé ne sont pas servis, et les fichiers remplacés
gardent leur ancienne taille et `ETag` (utilisez des variables d'environnement pour la configuration
à l'exécution)
- les `ETag`s pour les assets statiques sont des hashes du contenu, et `Last-Modified` n'est plus
envoyé
- seules les requêtes `GET` et `HEAD` servent des assets statiques ; les autres méthodes résultent
en une réponse 405

### `adapter-netlify`

- la sortie compilée est désormais conforme à l'[API stable de Netlify
Frameworks](https://docs.netlify.com/build/frameworks/frameworks-api/)
- déployer/prévisualiser avec le CLI de Netlify requiert la version `v17.31.0` ou plus récent (`npm
i -g netlify-cli@latest`)
- la cible de compilation des fonctions edge est `es2022`
- le dossier de publication est désormais une option d'adaptateur plutôt que lu depuis le fichier
`netlify.toml`

### `adapter-vercel`

- l'environnement d'exécution `edge` n'est plus supporté

### Changements dans l'API des adaptateurs [!VO]Adapter API changes

Pour les auteurs et autrices d'adaptateurs, il y a quelques changements supplémentaires :

- les adaptateurs peuvent augmenter la configuration de Vite avec des plugins supplémentaires
- `builder.config.kit` n'existe plus — la configuration vit désormais à la racine
- `builder.createEntries` a été supprimé — utilisez `builder.writeClient`, `builder.writeServer` et
`builder.writePrerendered` directement
- `builder.compress` renvoie une liste de fichires compressés
- `builder.mkdirp` et `builder.rimraf` sont dépréciés en faveur des méthodes `node:fs`
- `builder.generateManifest` a été supprimé — utilisez `builder.generateServerInstance` pour le
remplacer, et `builder.manifest` pour accéder au manifeste
- la classe `Server` exportée depuis le serveur compilé est dépréciée — utilisez l'objet `server`
écrit par `builder.generateServerInstance`

#### Instrumentation serveur [!VO]Server instrumentation

Les adaptateurs qui utilisent `builder.instrument` doivent désormais générer un initialiseur
d'environnement avant toute étape de compilation, incluez le module renvoyé en tant que point
d'entrée lors de cette étape, et passez son chemin final à `builder.instrument` :

```js
// @filename: ambient.d.ts
import { Builder } from '@sveltejs/kit';

declare global {
	const builder: Builder;
	const temporary_directory: string;
	const entrypoint: string;
	const instrumentation: string;
}

export {};

// @filename: index.js
// ---cut---
const initializer = builder.createInstrumentationInitializer({ outputDirectory: temporary_directory });

// Incluez `initializer` dans toute compilation ou suivi de fichier ici

builder.instrument({
	entrypoint,
	instrumentation,
	initializer
});
```

Pour les environnements d'exécution qui n'exposent pas de variables d'environnement via
`process.env`, passez le contenu d'un module dont l'export par défaut est la plateforme est
l'environnement de la plateforme :

```js
// @filename: ambient.d.ts
import { Builder } from '@sveltejs/kit';

declare global {
	const builder: Builder;
	const temporary_directory: string;
}

export {};

// @filename: index.js
// ---cut---
const initializer = builder.createInstrumentationInitializer({
	outputDirectory: temporary_directory,
	environment: `import { env } from 'cloudflare:workers';\nexport default env;`
});
```

## Réponses [!VO]Responses

### Les réponses 204 ne renvoie aucun contenu [!VO]204 responses return no content

Renvoyer une réponse `204` (ou toute réponse `2xx` vide) depuis un gestionnaire `+server.js` résulte
désormais en une réponse sans body, comme le requiert la spécification HTTP, plutôt qu'une enveloppe
SvelteKit. Le code qui consommait le body de telles réponses doit gérer le cas du body vide.

### `resolve` renvoie toujours une `Promise` [!VO]`resolve` always returns a `Promise`

La fonction `resolve` passée à [`handle`](hooks#handle) est désormais typée de manière à toujours
renvoyer une `Promise<Response>` plutôt qu'une `MaybePromise<Response>`.

## Modules réservés au serveur [!VO]Server-only modules

### Fichiers [!VO]Files

Les modules réservés au serveur sont désormais désignés par un nom de fichier ayant un segment
`server`, plutôt qu'un infixe `.server.` — autrement dit, `stuff.server.ts`, `stuff.server.test.ts`
et `server.ts` sont tous traités comme des modules réservés au serveur, alors qu'auparavant
`server.ts` ne l'était pas.

### Directories

Auparavant, tout module dans le dossier `src/lib/server` était traité comme réservé au serveur. Ce
traitement est désormais appliqué à _tout_ dossier `server` dans le projet, à l'exception de ceux
étant au sein des dossiers `src/routes` et `static`.

## Fonctions distantes [!VO]Remote functions

Les fonctions distantes sont toujours considérées expérimentales — activez-les via l'option
`experimental.remoteFunctions` en plus de `compilerOptions.experimental.async` :

```js
/// file: vite.config.js
import { defineConfig } from 'vite';
import { sveltekit } from '@sveltejs/kit/vite';
// ---cut---
export default defineConfig({
	plugins: [
		sveltekit({
			compilerOptions: {
				experimental: {
					+++async: true+++
				}
			},
			experimental: {
				+++remoteFunctions: true+++
			}
		})
	]
});
```

### Noms de fichiers de fonctions distantes [!VO]Remote module filenames

Comme avec les modules réservés au serveur, un segment `remote` dans un nom de fichier rend le
module distant — `stuff.remote.ts`, `stuff.remote.test.ts` et `remote.ts` sont tous des modules
distants.

Si `experimental.remoteFunctions` n'est pas activé, la présence de ces fichiers va provoquer une
erreur.

### `event.url`, `event.params`, et `event.route` ne sont pas accessibles au sein des queries [!VO]`event.url`, `event.params`, and `event.route` cannot be accessed inside queries

Accéder à `event.url`, `event.params`, ou `event.route` au sein d'une fonction distante `query`
jette désormais une erreur. Ces propriétés ne sont pas pertinente dans le contexte d'une fonction
distante (qui peut être appelée de n'importe où). Passez explicitement les valeurs dont vous avez
besoin en tant qu'arguments à la fonction.

### Les erreurs sont typées `App.Error | undefined` [!VO]Errors are typed as `App.Error | undefined`

La propriété `error` des ressources de fonctions distantes (les fonctions de type queries, live
queries, form, et prerender) est désormais typé en tant que `App.Error | undefined` plutôt que
`any`, puisque l'erreur est maintenant toujours transformée par `handleError`.

### Les soumissions de formulaire requièrent `field.as(...)` [!VO]Form submissions require `field.as(...)`

Un contrôle de formulaire doit utiliser les attributs d'un champ associé à l'objet `form` courant :

```svelte
<input {...myform.fields.message.as('text')}>
```

Préciser manuellement un nom (`<input name="message">`) va provoquer le rejet de la soumission.

## Divers [!VO]Miscellaneous

### Les liens vers la page courante provoquent un rafraîchissement [!VO]Links to the current page cause a refresh

Si un utilisateur clique sur un lien qui pointe vers la page courante, SvelteKit va exécuter
`refreshAll` plutôt que de ne rien faire.

### `data-sveltekit-*` utilise `false` plutôt que `'off'` [!VO]`data-sveltekit-*` uses `false` instead of `'off'`

La valeur `'off'` pour les attributs de lien `data-sveltekit-*` a été supprimée en faveur de
`false`.

```svelte
---<a href="..." data-sveltekit-preload-data="off">---
+++<a href="..." data-sveltekit-preload-data="false">+++
```

### Les redirections externes doivent être activées [!VO]External redirects must be opted into

Pour utiliser [`redirect`](@sveltejs-kit#redirect) vers une URL externe, vous devez désormais passer
une option `external` — soit `true` pour autoriser n'importe quelle URL externe (sauf les URLs
`javascript:`, qui sont toujours bloquées), soit un tableau d'origines autorisées (qui _peut_
inclure des URLs `javascript:`).

```js
import { redirect } from '@sveltejs/kit';
// ---cut---
redirect(307, 'https://example.com', +++{ external: true }+++);
```

### La `config` universelles a la priorité sur la config `server` [!VO]Universal `config` takes precedence over server `config`

Les `config` de route exportées depuis des fichiers `+page.js` ou `+layout.js` sont désormais
prioritaires par rapport aux `config` exportées depuis les fichiers `+page.server.js` ou
`+layout.server.js` correspondant, comme pour les autres options de page. Si vous exportez `config`
depuis les 2 fichiers, déplacez l'export canonique vers le fichier universel, ou consolidez-les.

### Les activations de service workers utilisent `type: 'module'` [!VO]Service worker registrations use `type: 'module'`

Les modules de service worker sont désormais largement supportés. Dès lors, SvelteKit va compiler et
activer vos service workers en tant que modules, plutôt qu'en tant que scripts.
