title: $app/tsconfig
---

Ce module contient la configuration TypeScript taillée pour votre application. Votre propre
configuration devrait en hériter — un fichier `tsconfig.json` typique ressemble à ceci :

```json
/// file: tsconfig.json
{
	"extends": "$app/tsconfig",
	"include": ["src", "test"],
	"exclude": ["src/service-worker"]
}
```

Vous pouvez étendre cette configuration avec vos propres `compilerOptions`. Écraser les propriétés
suivantes peut casser certaines choses — SvelteKit vous préviendra si cela se produit :
You can extend this configuration with your own `compilerOptions`. Overriding the following

- `paths` — ceci est dérivé depuis l'option (dépréciée) de configuration
[`alias`](configuration#alias), ainsi que de tout [import de
sous-chemin](https://nodejs.org/api/packages.html#subpath-imports) précisé dans votre fichier
`package.json`, pour aligner les comportements de Vite et TypeScript. Idéalement, configurez les
imports de sous-chemins plutôt que d'utiliser `paths` directement
- `types` — votre application a besoin d'être capable de 'voir' les déclarations de modules générés
  pour des choses comme les [variables d'environnement](environment-variables), par conséquent ce
tableau doit inclure `"$app/types"`
- `isolatedModules` — doit valoir `true`, puisque Vite compile les modules un à la fois
- `verbatimModuleSyntax` — doit valoir `true`, afin que vous puissiez utiliser sans accroc les
imports de type dans les fichiers `.svelte`

Notez que la configuration d'exemple présentée plus haut exclut `src/service-worker`, car les
service workers ont besoin d'être dans leur propre projet TypeScript. Si vous utilisez un service
worker, créez un fichier `src/service-worker/tsconfig.json` qui hérite de
[`$app/tsconfig/service-worker`]($app-tsconfig-service-worker).
