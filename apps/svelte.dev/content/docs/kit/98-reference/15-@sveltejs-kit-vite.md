## sveltekit

Le plugin Vite de SvelteKit, qui doit être ajouté à votre fichier `vite.config.js`, avec votre
configuration de projet :

```js
// @errors: 7031
/// file: vite.config.js
import adapter from '@sveltejs/adapter-auto';
import { sveltekit } from '@sveltejs/kit/vite';
import { defineConfig } from 'vite';

export default defineConfig({
	plugins: [
		sveltekit({
			adapter: adapter(),
			compilerOptions: {
				experimental: {
					async: true
				}
			},
			experimental: {
				remoteFunctions: true
			}
		})
	]
});
```

Comme pour SvelteKit, les options de plugin sont utilisées par d'autres outillages qui s'intègrent
avec Svelte, comme des extensions d'éditeurs.

Toute option n'appartenant pas à SvelteKit passe par
[`vite-plugin-svelte`](https://github.com/sveltejs/vite-plugin-svelte/blob/main/docs/config.md),
afin que vous puissiez également définir ici des options commen `inspector`. Le namespace
`experimental` est partagé — SvelteKit lit ses propres propriétés et relaie le reste.

> [!LEGACY]
> Avant SvelteKit 3, la configuration était définie dans un fichier `svelte.config.js`, qui n'est
> plus supporté. La possibilité de configurer SvelteKit via `vite.config.js` a été ajoutée dans la
> version 2.62.

## csp

<div class="ts-block-property-bullets">



</div>

La configuration
[Content Security
Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy). Les CSPs
vous attendent à protéger vos utilisateurs contre les attaques de type "cross-site scripting" (XSS),
en limitant les endroits depuis lesquels les ressources peuvent être chargées. Par exemple, une
configuration comme celle-ci :

```js
// @errors: 7031
/// file: vite.config.js
import { sveltekit } from '@sveltejs/kit/vite';
import { defineConfig } from 'vite';

export default defineConfig({
	plugins: [
		sveltekit({
			csp: {
				directives: {
					'script-src': ['self']
				},
				// doit être précisé avec soit la directive `report-uri`, soit la directive
				// `report-to`, soit les deux
				reportOnly: {
					'script-src': ['self'],
					'report-uri': ['/']
				}
			}
		})
	]
});
```

... va empêcher le chargement des scripts depuis des sites externes. SvelteKit va augmenter les
directives précisées avec des nonces ou des hashes (selon le `mode`) pour tous les scripts et les
styles inlinées qu'il génère.

Pour ajouter un nonce pour les scripts et les liens manuellement inclus dans `src/app.html`, vous
pouvez utiliser un placeholder `%sveltekit.nonce%` (par exemple `<script
nonce="%sveltekit.nonce%">`).

Lorsque les pages sont prérendues, l'en-tête CSP est ajoutée via une balise `<meta http-equiv>`
(notez que dans ce cas, les directives `frame-ancestors`, `report-uri` et `sandbox` seront
ignorées).

> [!NOTE] Lorsque le `mode` est `'auto'`, SvelteKit va utiliser des nonces pour les pages rendues
> dynamiquement et des hashes pour les pages prérendues, L'utilisation de nonces pour les pages
> prérendues est dangereuse et est donc procscrite.

Si ce niveau de configuration est insuffisant pour vos contraintes spécifiques, vous pouvez utiliser
le [hook `handle`](/docs/kit/hooks#handle) pour définir vos propres CSP.

## csrf

<div class="ts-block-property-bullets">



</div>

Une protection contre les attaques de type [cross-site request forgery
(CSRF)](https://owasp.org/www-community/attacks/csrf).

<div class="ts-block-property-children">

<div class="ts-block-property">

</div>

Si oui ou non vérifier si l'en-tête entrante `origin` pour les soumissions de formulaire `POST`,
`PUT`, `PATCH`, ou `DELETE` correspond à l'origine du serveur.

Pour permettre aux gens de faire des requêtes `POST`, `PUT`, `PATCH`, or `DELETE` vers votre
application depuis d'autres origines avec un `Content-Type` valant
`application/x-www-form-urlencoded`, `multipart/form-data`, ou `text/plain` , vous aurez besoin de
désactiver cette option. Soyez prudent·es !

</div>
</div>
<div class="ts-block-property">

```ts
// @noErrors
trustedOrigins?: string[];
```

<div class="ts-block-property-details">

<div class="ts-block-property-bullets">

- <span class="tag">par défaut</span> `[]`

</div>

Un tableau des origines autorisées à faire des requêtes de soumissions de formulaire cross-origin
vers votre application.

Chaque origine doit être complète et inclure un protocole (par ex. `https://payment-gateway.com`).
Ceci permet aux services tiers de confiance comme les portails de paiement ou les fournisseurs
d'authentification de soumettre des formulaires vers votre application.

Si le tableau contient `'*'`, toutes les origines seront considérées de confiance. Ceci est
généralement non recommandé !

> [!NOTE] N'ajoutez que des origines auxquelles vous faites entièrement confiance, puisque ceci
> contourne la protection CSRF pour ces origines.

Les vérifications CSRF ne s'appliquent qu'en production, pas pendant le développement local.

## embedded

<div class="ts-block-property-bullets">

- <span class="tag">par défaut</span> `false`

</div>

Si oui ou non l'application est intégré au sein d'une application plus large, Si vaut `true`,
SvelteKit va ajouter ses gestionnaires d'évènement liés à la navigation (et autre) sur le parent de
`%sveltekit.body%` plutôt que `window`,

Whether or not the app is embedded inside a larger app. If `true`, SvelteKit will add its event
listeners related to navigation etc on the parent of `%sveltekit.body%` instead of `window`, and
will pass `params` from the server rather than inferring them from `location.pathname`.
Note that it is generally not supported to embed multiple SvelteKit apps on the same page and use
client-side SvelteKit features within them (things such as pushing to the history state assume a
single instance).

## inlineStyleThreshold

<div class="ts-block-property-bullets">

- <span class="tag">par défaut</span> `0`

</div>

Inline le CSS dans un bloc `<style>` en haut du HTML. Cette option est un nombre qui précise la
longueur maximale d'un fichier CSS à inliner en unité de code UTF-16, comme spécifié par la
propriété [String.length](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/String/length).
All tous les fichiers CSS nécessaires pour la page qui sont plus petits que cette valeur sont
fusionnés et inlinés dans un bloc `<style>`.

> [!NOTE] Ceci réduit le nombre de requêtes initiales, et peut améliorer votre score de [First
> Contentful Paint](https://web.dev/first-contentful-paint). Cependant, il génère des fichiers HTML
> plus lourds et réduit en conséquence l'efficacité des caches de navigateur. À utiliser avec
> précaution.

<div class="ts-block-property">

```ts
// @noErrors
preloadStrategy?: 'modulepreload' | 'preload-js' | 'preload-mjs';
```

<div class="ts-block-property-details">

<div class="ts-block-property-bullets">

- <span class="tag">par défaut</span> `"modulepreload"`
- <span class="tag since">disponible depuis la version</span> v1.8.4
- <span class="tag deprecated">déprécié</span> supprimé dans la version 3.0

</div>

SvelteKit va précharger les modules JavaScript nécessaires pour le rendu initial de la page afin
d'éviter des "cascades" de chargement, accélérant ainsi le démarrage de l'application. Il y a trois
stratégies avec différents compromis :
- `modulepreload` – utilise `<link rel="modulepreload">`. Ceci fournit de meilleurs résultats pour
les navigateurs basés sur Chrome, pour Firefox 115+, et Safari 17+. Cette option est ignorée pour
les navigateurs plus anciens.
- `preload-js` – utilise `<link rel="preload">`. Empêche les cascades dans Chromium et Safari, mais
Chromium va parser chaque module deux fois (une fois en tant que script, une fois en tant que
module). Dans Firefox les modules seront requêté deux fois. C'est une bonne option si vous souhaitez
maximiser les performances pour les utilisateurs et utilisatrices d'appareils mobiles au prix d'une
légère dégradation sur Chromium.
- `preload-mjs` – utilise `<link rel="preload">` mais avec l'extension `.mjs`, qui empêche le double
parsing sur Chromium. Certains serveurs web statiques échouent à servir les fichiers `.mjs` ayant
une en-tête `Content-Type: application/javascript`, ce qui va casser votre application. Si vous
n'utilisez pas ce genre de serveur, cette option est celle qui fournira les meilleures performances
pour le plus grand nombre d'utilisateurs et utilisatrices, le temps que `modulepreload` soit plus
largement supporté.

</div>
</div>
<div class="ts-block-property">

```ts
// @noErrors
bundleStrategy?: 'split' | 'single' | 'inline';
```

<div class="ts-block-property-details">

<div class="ts-block-property-bullets">

- <span class="tag">par défaut</span> `'split'`
- <span class="tag since">disponible depuis la version</span> v2.13.0

</div>

La stratégie de compilation affecte la manière dont les fichiers JavaScript et CSS de votre
application sont chargés.
- Si vaut `'split'`, découpe votre application en plusieurs fichiers `.js`/`.css` afin qu'ils soient
chargés au fur et à mesure que l'utilisateur ou utilisatrice navigue dans votre application. C'est
la valeur par défaut, et est recommandée pour la plupart des scénarios.
- Si vaut `'single'`, crée un seul bundle `.js` et un seul fichier `.css` contenant touet le code de
votre application
- Si vaut `'inline'`, inline tout le JavaScript et tout le CSS de l'application dans le HTML. Le
résultat est utilisable sans serveur (c-à-d que vous pouvez simplement ouvrir le fichier dans votre
navigateur).

Lorsque vous utilisez `'split'`, vous pouvez également ajuster le comportement de compilation en
définissant [`output.codeSplitting`](https://rolldown.rs/reference/OutputOptions.codeSplitting) dans
l'option [`build.rolldownOptions`](https://vite.dev/config/build-options#build-rolldownoptions) de
votre configuration Vite.

Si vous souhaitez inliner vos assets, vous devez définir l'option
[`build.assetsInlineLimit`](https://vite.dev/config/build-options.html#build-assetsinlinelimit) de
Vite à une taille appropriée, puis importer vos assets via Vite.

```js
// @errors: 7031
/// file: vite.config.js
import { sveltekit } from '@sveltejs/kit/vite';
import { defineConfig } from 'vite';

export default defineConfig({
	plugins: [sveltekit()],
	build: {
		// inline tous les assets importés
		assetsInlineLimit: Infinity
	}
});
```

```svelte
</script>

<svelte:head>

</svelte:head>
```

Quel type de routeur client utiliser.
- `'pathname'` est la valeur par défaut, et signifie que le chemin de l'URL courante
détermine la route
- `'hash'` signifie que la route est déteminé par `location.hash`. Dans ce cas, le SSR

</div>
<div class="ts-block-property">

```ts
// @noErrors
resolution?: 'client' | 'server';
```

<div class="ts-block-property-details">

<div class="ts-block-property-bullets">

- <span class="tag">par défaut</span> `"client"`
- <span class="tag since">disponible depuis la version</span> v2.17.0

</div>

Comment déterminer quelle route charger lorsque l'on navigue vers une nouvelle page.

Par défaut, SvelteKit va servir un manifeste de routes au navigateur. Lors de la navigation, ce
manifeste est utilisé (de paire avec le hook `reroute`, s'il existe) pour déterminer quels
composants charger et quelles fonctions `load` exécuter. Puisque tout se passe côté client, cette
décision peut être faite immédiatement. L'inconvénient est que le manifeste a besoin d'être chargé
et parsé avant que la première navigation ne se produise, ce qui peut avoir un impact si votre
application contient beaucoup de routes.


Une autre option est que SvelteKit détermine la route sur le serveur. Ceci implique que pour chaque
			navigation vers un chemin qui n'a pas encore été visité, le serveur sera sollicité pour
			déterminer la route.
Ceci a plusieurs avantages :
- Le client n'a pas besoin de charger le manifest de routes immédiatement, ce qui amener des temps
de chargement initiaux plus rapides
- La liste des routes est cachée du public
- Le serveur a une opportunité d'intercepter chaque navigation (par exemple au travers d'un
middleware positionné devant SvelteKit, comme un proxy ou les fonctions edge de votre plateforme),
permettant (par exemple) de faire de l'A/B testing dont SvelteKit n'a pas conscience.

La réponse à une requête de résolution de routes est envoyée dès que la route a été trouvée, avant
l'invocation du hook `handle`. Pour les intercepter au sein de SvelteKit lui-même, utilisez le hook
`reroute`, qui est également exécuté pour ces requêtes.

L'inconvénient est que pour des chemins non visités, la résolution prendra un peu plus de temps
(bien que ceci peut être compensé par du
[préchargement](/docs/kit/link-options#data-sveltekit-preload-data)).

> [!NOTE] Lorsque vous utilisez la résolution de routes côté serveur avec du pré-rendu, la
> résolution est pré-rendue avec la route elle-même.

## version

<div class="ts-block-property-bullets">



</div>

La navigation client peut mal fonctionner si vous déployer une nouvelle version de votre application
pendant que des gens sont en train de s'en servir. Si le code de la nouvelle page est déjà chargé,
il peut contenir du contenu périmé ; s'il n'est pas encore chargé, le manifeste de routes de
l'application peut pointer vers un fichier qui n'existe plus.
SvelteKit vous aide à résoudre ce problème avec de la gestion de version. La version actuelle est
incluse dans les réponses de données, de fonctions distantes et d'actions de formulaire via
l'en-tête `x-sveltekit-version`, afin que SvelteKit puisse détecter de nouveaux déploiements sans
faire de polling — par exemple lorsqu'une navigation déclenche l'exécution d'une fonction `load` de
serveur, ou lorsque une fonction distante est appelée. SvelteKit vérifie également si une nouvelle
version est disponible lorsque l'onglet récupère le focus ou devient visible.
Si SvelteKit rencontre une erreur pendant le chargement de la page et détecte qu'une nouvelle
version a été déployée (en utilisant le `name` précisé ici, qui est par défaut le timestamp au
moment de la compilation), il va se rabattre sur une navigation complète traditionnelle.

Mais toutes les navigations ne vont pas provoquer une erreur, par exemple si le code JavaScript de
la prochaine page est déjà chargé. Si vous souhaitez tout de même forcer une navigation complète
dans ces cas-là, utilisez `beforeNavigate` :

```html
/// file: +layout.svelte
<script>
	import { beforeNavigate } from '$app/navigation';
	import { updated } from '$app/state';

	beforeNavigate(({ willUnload, to }) => {
		if (updated.current && !willUnload && to?.url) {
			location.href = to.url.href;
		}
	});
</script>
```

En complément de ces vérifications, SvelteKit vérifie l'existence de nouvelles versions à intervalle
régulier et met [`updated.current`](/docs/kit/$app-state#updated) à `true` lorsqu'il en détecte une.
Mettez `pollInterval` à `0` pour désactiver cet intervalle (les vérifications mentionnées plus haut
utilisant l'en-tête et les évènements vont toujours avoir lieu).

<div class="ts-block-property-children">

<div class="ts-block-property">

```ts
// @noErrors
name?: string;
```

<div class="ts-block-property-details">

La chaîne de caractères représentant la version de l'application. Si précisé, cette valeur doit être
déterministe (par ex. une référence de commit plutôt que `Math.random()`, ou
`Date.now().toString()`), et vaut par défaut un timestamp du moment de la compilation.

Par exemple, pour utiliser le hash du commit actuel, vous pouvez utiliser `git rev-parse HEAD` :

```js
// @errors: 7031
/// file: vite.config.js
import * as child_process from 'node:child_process';
import { sveltekit } from '@sveltejs/kit/vite';
import { defineConfig } from 'vite';

export default defineConfig({
	plugins: [
		sveltekit({
 		version: {
				name: child_process.execSync('git rev-parse HEAD').toString().trim()
			}
		})
	]
});
```

</div>
</div>
<div class="ts-block-property">

```ts
// @noErrors
pollInterval?: number;
```

<div class="ts-block-property-details">

<div class="ts-block-property-bullets">

- <span class="tag">par défaut</span> `3600000`

</div>

L'intervalle en millisecondes à utiliser pour faire les vérifications de changements de version
("polling"). Si cet intervalle est `0`, aucun intervalle n'est lancé. SvelteKit vérifie également
l'existence de nouvelles versions lors des réponses du serveur (via l'en-tête `x-sveltekit-version`)
et lorsque l'onglet récupère le focus ou devient visible, ce qui fait que le polling n'est
nécessaire que pour les sessions longues sur une seule page.


</div>
</div>
